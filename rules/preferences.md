# 偏好与规范

保持偏好（怎么写）、契约（行为）、计划（怎么改）三层分离。偏好只补充项目材料没有表达的硬约束，不承担技术栈说明书的职责。

## 1. 双层模型

| 层级 | 文件 | 作用范围 |
|------|------|----------|
| L1 | `<skill>/preferences/global-preferences.md` | 个人跨项目习惯；专属技术规则须注明适用条件 |
| L2 | `<repo-root>/agent_docs/preferences/project-rules.md` | 当前项目或明确标注的模块；可不存在 |

解析统一见 `rules/project-context.md` §3：遵守用户和宿主项目指令，在此边界内适用的 L2 > L1 > 项目证据 > 通用默认。先判断适用性，不能让某语言库或旧项目组件成为所有项目的要求。

## 2. 阶段 0 加载

读取简短 L1、已有 L2 和相关项目指令；结合当前模块配置与同类实现，合并工作记忆中的生效规则。切换项目时重新解析，不沿用上一项目的技术选择。无需生成持久化档案。

## 3. 各阶段生效

| 阶段 | 作用 |
|------|------|
| 1 澄清 | 复用已知约束，不重复询问已明确的技术选择 |
| 2 契约 | 按项目实际定义输入/输出、错误、状态、鉴权与兼容性 |
| 3 计划 | 对齐实际目录、组件和测试/验收命令；引用来源 |
| 4 TDD | 按目标模块工具执行测试，核对作用范围、前置条件与质量要求 |
| 5 测试包 | 按实际协议和响应行为生成断言，不默认响应封装 |

## 4. 无 L2 时

不阻塞，不要求初始化，不因缺文件而自动生成规范。配置和项目指令足够就直接用；规则反复需要解释且无法从现有材料得知时，才简短建议保存。

## 5. 输出

与 `project-context.md` §4 合并为最多两行，不复述正文、不重复确认。真正冲突只在需要决策时提出。

## 6. 辅助保存（用户触发）

用户要求保存时，参考 `<skill>/preferences/project-rules.template.md`，基于已有证据先起草；缺少会改变规则的事实时一次只问一个问题。

只保存：明确的特殊约束、必须复用的组件、非显然的运行条件和必要来源指针。注明模块范围，保留人工条目，不虚构规则；不把本次需求与技术偏好混写。人类可读文本中文，代码/路径/命令/标识保持原样。

## 7. 与项目指令的关系

项目指令继续由宿主按其作用范围加载；偏好文档在 PTDD 激活后由 PTDD 显式读取。二者不能假设会自动合并，也不能把偏好声明成绕过项目硬约束的权限。
