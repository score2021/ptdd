# TDD 实施规则

只在用户明确授权实施且已有确认的计划与契约后进入。语言和项目形态由阶段 0 识别，测试工具、文件组织与验证入口复用当前模块；不固定语言、库、运行时或分层。

## 检查清单（按计划维护）

- [ ] 步骤 0：核对测试环境、基线、验收命令与运行目录。
- [ ] 步骤 1-2：按契约编写可观察行为测试。
- [ ] 步骤 3：运行，确认目标行为缺失造成有效 RED。
- [ ] 步骤 4-5：最小实现，运行相同测试确认 GREEN。
- [ ] 步骤 5.5：检查修改范围，保护用户已有改动。
- [ ] 步骤 5.6：涉及字段映射则核对来源与易混字段测试；不涉及时注明不适用。
- [ ] 步骤 6：重构，保持测试通过。
- [ ] 步骤 7：相关回归、覆盖率 ≥ 80% 和项目约定验收链。

每个任务及时更新清单，完成前逐项核对。不能删除计划任务、擅改契约、跳过有效 RED，或未验收就宣称完成。

## 步骤 0.1：测试环境与基线

1. 读取已确认计划、契约及阶段 0 选定的项目来源，核对目标模块的运行时、依赖环境、测试配置和发现规则。
2. 检查已有测试链是否可运行，记录基线失败、测试数量和前置条件。原有失败要如实报告，不伪装成新功能的 RED。
3. 工具或依赖缺失时先说明缺口；仅按用户授权与计划配置必要环境，不自动安装默认测试库、替换包管理器或修改锁文件。
4. 模块无测试入口时，在计划确认最小测试方案再实施；无数据库、HTTP 或浏览器需求时不额外建设对应基础设施。

## 步骤 0.2：确认命令与质量要求

规则解析见 `rules/project-context.md` §3。核对项目指令、实际脚本/任务、CI 与适用偏好；命令必须存在、参数适合实际 runner，并在正确模块目录执行。

区分：定向测试、相关/模块回归、项目约定全链、类型检查、构建、静态检查和覆盖率。不能把一种验证当作另一种已通过。缺少可靠命令时先在阶段 1/3 确认，不根据语言名称猜命令。

覆盖率 ≥ 80%，明确语句/行/分支等实际指标、生产代码统计范围与排除项，沿用项目更严格阈值；不拿不同工具的百分比直接等同。无覆盖率工具时报告未验证并补齐已确认的最小方案，不能仅因测试通过就声称达到门槛。不用新增排除项或只统计已导入文件来凑覆盖率。

## 步骤 1-3：行为测试与 RED

- 每个本次新增/修改的行为先有测试，覆盖正常、失败与适用边界。测试依据契约，不为每个私有函数机械创建测试。
- 先运行测试确认其被实际发现，并因预期行为尚未实现而失败。新增接口缺失造成的编译/类型失败，只有在测试发现与基础环境正常且明确指向待实现接口时才可作为 RED，并记录原因。
- 命令错误、缺依赖、导入/配置损坏、未发现测试和不相关的已有故障都不是有效 RED。
- 不把 `passWithNoTests`、空筛选、skip/xfail/todo/only 等造成的漏跑当作通过；本次范围内不得遗留为绕过失败而加的跳过/禁用标记，项目原有项单独报告。

## 步骤 4-5：GREEN

只实现让目标行为通过的最小改动，重复运行对应测试。断言真实结果、业务错误/异常、状态、副作用和协议契约，不用只检查 mock 调用或测试实现细节来冒充行为验证。

依赖优先用项目已有的注入点、fixture、stub、mock；遵守显式禁区。时间、随机、网络、文件系统等依赖应可控制，替换状态在测试后恢复；禁止跨测试泄漏状态。不要为单测重造生产架构。

## 步骤 5.5：修改范围

仅修改计划列出的文件；发现必要的范围外改动时先说明并更新计划，按原流程取得授权。保护用户未提交内容，不清理未知文件。检查规则见 `rules/plan-git-hygiene.md`。

## 步骤 5.6：查询字段映射

新增/修改筛选、排序、聚合、唯一性或状态映射时，检查请求语义、模型、schema/迁移/存储字段及实际条件。为易混字段构造能区分错误映射的测试，验证空值是否意外返回全量。

优先断言可观察结果；必要时采用项目已有的查询构造测试方式，不仅为断言而创建生产 helper，不连接生产数据库。不涉及查询/映射则注明不适用。细则见 `rules/plan-field-mapping.md`。

## 步骤 6：REFACTOR

绿色后清理重复和命名，保持对外行为与契约不变，再跑目标测试。协议 JSON 按结构和契约断言，不能依赖对象键顺序；动态值与可选字段按契约处理。golden/snapshot 是正式资产，不随意更新以掩盖错误，行为变更须先同步契约与计划。

## 步骤 7：最终验收与交接

- 运行计划约定的定向、相关回归和 Build & Verify 全链；多模块分别在正确环境执行，并检查必要的跨模块契约。
- 核实测试实际运行数量、退出状态和覆盖率指标，不遗漏 stderr 中的失败。遵守项目性能预算，开发中优先短反馈，不把固定秒数强套到所有套件。
- 分别列已通过、失败、未运行及不适用项；测试全绿不代表类型检查、构建或集成验收已完成。
- 检查正式测试与必要 fixture 在交付范围，临时输出按政策处理；不主动 git add/commit/push。
- 所有任务与适用验收项通过后，按主流程阶段 4→5 重门控交接，询问是否生成可选接口测试包；未通过时如实停在对应问题，不称“全部完成”。

## 禁止

- 先实现再补测试；把环境故障或零测试当 RED/GREEN。
- 删除/放宽业务断言、降低覆盖率或改 golden 来凑通过。
- 将旧项目的技术库、错误模型、目录或命令带入当前项目。
- 未获授权改范围外文件、安装无关依赖或提交代码。
