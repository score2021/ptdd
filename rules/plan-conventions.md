# 项目惯例对齐

涉及请求边界、交互状态、日志、错误、数据访问、事务、任务、外部 client 或鉴权时读取。不要求必须先存在 AGENTS.md；配置、同类实现同样可提供证据。

## 1. 目录与架构

使用阶段 0 确认的模块结构和职责边界。计划列真实相对路径与同类实现，不把某语言、框架或旧项目的分层套到新项目。目录缺失时依据已确认方案安排，不照抄示例文件名。

## 2. 测试组织

沿用目标模块已有的测试目录、发现规则、命名、运行环境和依赖替换方式；区别单元、契约、集成与端到端测试。多模块分别注明命令运行目录，前端交互测试不能用服务端请求测试冒充。

## 3. 复用基础能力

计划中简短写清：1-3 个同类实现路径和符号、拟复用组件、是否新增抽象及必要性。复用实际请求校验、状态管理、数据访问、错误转换和日志方式；不用旧项目组件名作为通用要求。

无可复用组件时只提出满足本次需求的最小方案，不为单测便利增加生产 wrapper，不无理由重构架构。

## 4. 验收命令

复用阶段 0 确认的项目指令、任务脚本、测试配置与 CI；记录命令、工作目录、前置条件和预期结果。实际声明脚本名称不能猜；定向测试参数必须符合实际 runner/脚本。测试、类型检查、构建、lint 与覆盖率按项目能力分别列出；不适用项说明原因，不临时引入整套工具。

## 5. 文档归档

| 产物 | 默认路径 |
|------|----------|
| 契约 | `agent_docs/contracts/YYYY-MM-DD-<feature>-contract.md` |
| 计划 | `agent_docs/plans/YYYY-MM-DD-<feature>-plan.md` |
| HTTP 测试包 | `agent_docs/api-tests/YYYY-MM-DD-<feature>.postman_collection.json` |
| 用户要求保存的少量项目规则 | `agent_docs/preferences/project-rules.md` |

遵守项目已有文档政策；只在保存实际产物时创建必要目录，不额外建空树。人类可读文本中文，代码/命令/路径/机器标识保持原样。测试源码放项目测试位置，不能因由 AI 生成就移入文档目录。
