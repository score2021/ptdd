# Brainstorming 阶段规则

本文档整合了需求澄清（Brainstorming）阶段的所有关键规则。

---

## 规则 1：- 首先检查当前项目状态（文件、文档、最近的提交）

---

## 规则 2：一次只问一个问题

**影响级别**：CRITICAL

在需求澄清阶段，**必须**一次只问一个问题，避免用户被多个问题压倒。

---

## 规则 3：探索 2-3 种替代方案

**影响级别**：CRITICAL

在确定最终方案之前，**必须**提出 2-3 种不同的技术方案及其权衡。

---

## 规则 4：分段验证设计

**影响级别**：HIGH

在呈现设计时，**必须**分段展示并逐段验证（每段 100-150 字）。

---

## 规则 5：YAGNI - You Aren't Gonna Need It

**影响级别**：CRITICAL

**无情地移除不必要的功能**。只实现当前确实需要的部分。

---

## 规则 6: 呈现设计原则

- **一旦你相信理解了要构建的内容，呈现设计概要**
- **保持简洁**：每个部分 100-150 字，只描述关键要点
- **聚焦高层设计**：架构思路、核心 API、关键决策点
- **避免过早细节**：不要在此阶段展开具体实现代码、详细类型定义、完整测试用例
- **在每节后询问**是否看起来正确
- **准备好回溯和澄清**，如果某些内容不合理
- **开发策略为测试驱动开发**：以测试驱动开发的方式进行开发、重构等方案设计

---

## 规则 7：尊重偏好与项目既有约定

**影响级别**：HIGH

阶段 0 已加载偏好文档（L1/L2）和 AGENTS.md（加载/降级逻辑见 `rules/project-context.md`）。
brainstorm 阶段**必须**遵循已生效的规则表：

### 7.1 不重复发问

不询问偏好文档 / AGENTS.md 已说明的事。例如已写明：
- "已确认使用项目现有数据访问组件" → **不问**"是否换一个 ORM"
- "错误使用项目统一类型/异常模型" → **不问**"错误怎么处理"
- "已有明确的模块/转换逻辑目录" → **不问**"是否新建另一套分层"
- "对外契约 JSON 字段不可改" → **不问**"是否可改字段名"

### 7.2 适用偏好 / ALWAYS / NEVER 作为硬约束

方案对比时，按 `rules/project-context.md` §3 解析作用范围和冲突，**不输出违反生效硬规则的方案**。例如：
- 项目要求内部错误在边界转换 → 不提“直接暴露内部错误详情”作为候选
- ALWAYS 写"contract test 必跑" → 任何方案都必须包含契约测试链路

### 7.3 按场景触发指针读取（仅加载到 AGENTS.md 时）

需求命中 AGENTS.md "Progressive Disclosure Index" 的场景时，**先读对应文档再设计方案**：
只读取实际指针指向的文件；没有指针时按需读同类实现，不要求建立固定名称的文档。

### 7.4 不复述项目文档

读到的偏好/项目文档**仅用于内部决策**，不原文贴进对话。引用时只说
"按 contracts.md §3 的契约护栏..."，不复制全段。

**禁止行为**：
- ❌ 给出违反偏好硬规则 / ALWAYS / NEVER 的方案
- ❌ 把读到的偏好/项目文档原封不动贴进对话
- ❌ 问已经在偏好文档 / AGENTS.md 里写明白的问题

> 无 AGENTS.md / 无 L2 时本规则按 `rules/project-context.md` §5 降级，不阻塞。
