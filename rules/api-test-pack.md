# 接口测试包

保持阶段 5 可选，也支持用户明确请求仅生成指定接口测试包的独立调用。基于契约生成 HTTP 接口的 Postman Collection v2.1（含请求、curl 与断言），供 Apifox/Postman 导入；本阶段生成资产，不默认执行请求或加入 CI。

## 1. 来源与适用性

来源顺序：用户指定契约 → 当前相关契约 → 指定/当前计划 → 目标项目路由/边界实现及 diff 推断。不要只因文件最新就选取其他需求或项目的契约；推断清单须先确认。

列本次接口与范围并确认后生成。已有契约是预期行为真源，源码用于核对现状；冲突先提示确认，不按源码静默改期望。

只为可表达的 HTTP 行为生成 Collection。纯函数、前端、CLI 或其他不适用协议说明原因，按主流程交接结束或由用户选择项目已有工具，不强造 HTTP 场景。语言不影响 HTTP 测试包的适用性，Postman 断言使用 JavaScript 不代表业务必须使用该语言。

## 2. 场景枚举

按实际契约覆盖正常、必填/类型失败、边界、权限、字段互斥/优先级、分页筛选、上传和异步行为；不要求每个接口都有所有维度。必填规则来自实际 schema、校验器或类型，不能只识别某框架 tag。

异步成功按契约确认任务接收/状态/副作用，不凭 URL 前缀放宽为“HTTP 200 即可”。有破坏性或环境敏感的测试数据操作要明确前置条件，不能擅自运行。

超过 30 条用例时先确认覆盖深度，其他情况不额外增加确认层。

## 3. 断言与变量

- HTTP 状态、Content-Type、JSON/文本/空响应/二进制表示、业务成功条件均来自当前契约，不固定 `200`、`code=0`、`data.rows` 或鉴权方式。
- 每个用例至少一个适用的行为断言；有业务结果时不能只断言传输成功。空响应按契约检查状态、header 或其他可观察结果，不强行解析 JSON。
- 先检查必需字段存在与类型，再检查内容。不得用 `value || []` 将缺字段伪装为空数组，也不得只在数组非空时执行关键断言。
- 已约定命中记录的场景断言必要数量/标识，确保数据为空不会静默通过；允许空结果的场景按契约单独断言。
- host、token、测试数据与环境参数用 `{{variable}}`，不硬编码真实凭据；断言需要取值时统一采用 `pm.variables.get(name)`，示例与规则一致，导入后核验目标工具变量优先级。
- Collection 级只放真正共同的检查；不同响应状态/格式的接口使用局部断言，不让全局模板覆盖差异。

## 4. 格式与交付

默认保存到 `agent_docs/api-tests/YYYY-MM-DD-<feature>.postman_collection.json`，遵守项目政策。请求与 curl 覆盖选定范围；脚本 `event[].script.exec` 是逐行字符串数组，字段类型符合 v2.1 schema。

生成后检查 JSON 可解析、变量引用完整、请求与契约对应、断言覆盖正常/失败/边界且不会因缺字段/空数组跳过。静态检查成功不等于真实请求通过，也不等于已验证特定工具版本可导入。

交付路径、变量名称与配置方式、用例数/分组、必要前置条件和未验证项。不把环境变量值、token 或真实数据放入说明。

人类可读名称、场景与断言名称用中文，JSON key、代码、路径和机器标识保持原样。该资产与阶段 4 的自动化测试互补，不替代 TDD。
